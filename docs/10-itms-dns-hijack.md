# 10 · 最终定案：ITMS 未注册导致 DNS 被劫持

> 这一章是整套教程的**结论修正篇**。前面 01~09 讲的是「桥接没做干净」这一类常见坑；但在本次设备上，真正让全网 DNS 失效的不是 LAN 侧残留，而是**光猫的 ITMS 注册状态**。
>
> 如果你遇到的现象是「能拨号、能拿到公网 IP、TCP/IP 一切正常，只有 IPv4 UDP/53 的域名全被解析成光猫管理地址」，直接看这一章。

---

## 0. 症状

| 现象 | 表现 |
|---|---|
| 主路由拨号 | 成功，拿到公网 IP，网关正常 |
| DNS | 所有域名（含随机不存在的域名）都返回 `A = 光猫管理地址`，TTL 3600 |
| 换路由器 | 无效，任何品牌都一样 |
| 重启光猫 | 无效 |
| TCP/53 | 正常，能拿到真实地址 |
| IPv6 DNS | 正常，能拿到真实 AAAA/A 记录 |
| DoH / DoT | 正常 |
| 直连真实 IP | 网页 200，链路完全健康 |

一句话：**只有 IPv4 UDP/53 这一个端口被劫持，其他一切正常。**

---

## 1. 根因

中兴方案的 GPON ONT 在 **ITMS 未注册**状态下，会在内核里启用 DNS 劫持：把桥接/PPPoE 路径上的 IPv4 UDP/53 查询就地伪造应答，全部指向自身 LAN 地址。设计意图是把用户引导到「设备注册」页面，副作用是让用户以为宽带完全不通。

判定只需一条命令：

```sh
export ZTE_PASS='<telnet 密码>'
python3 tools/zte_cmd.py "sendcmd 1 DB p PDTCTUSERINFO"
```

关键字段：

```
Status  = 99     ← 99 = ITMS 未注册（正常应为 0）
Result  = 99
CheckRegistEnable = 1
```

其他字段（`Times` / `FirstRegisted` / `ServiceResult` 等）不用管。

---

## 2. 修复

```sh
sendcmd 1 DB set PDTCTUSERINFO 0 Status 0
sendcmd 1 DB set PDTCTUSERINFO 0 Result 1
sendcmd 1 DB save
reboot
```

**必须重启。** 内核模块只在启动阶段读取该标志，改完不重启不会生效；重启后配置库里的值会保持。

仓库里的一键脚本：

```sh
python3 tools/fix_itms_dns.py --check      # 只查看状态
python3 tools/fix_itms_dns.py              # 写入并重启，等待上线
```

> ⚠️ **不要给这台光猫恢复出厂设置。** 重置会把状态打回未注册，DNS 立刻再次被劫持。若状态被平台重新下发成 99，重跑一次脚本即可。

---

## 3. 验证

重启并等光猫上线后，从终端侧发查询：

```sh
# 向公共 DNS 查一个存在的域名：应返回真实公网地址
python3 tools/probe_dns.py 223.5.5.5 --iface <你的网卡>

# 查一个随机不存在的域名：应返回 NXDOMAIN (rcode=3)，而不是 A 记录
```

通过主路由查询也应返回真实地址：

```sh
python3 tools/probe_dns.py <主路由管理地址> --iface <你的网卡>
```

再实际访问一个网站确认端到端可用。三步都过才算修完。

---

## 4. 为什么其他办法都无效（弯路记录）

| 尝试 | 结果 | 原因 |
|---|---|---|
| 换主路由 | 无效 | 劫持发生在光猫 PPPoE 路径上，与路由品牌无关 |
| 主路由手动指定公共 DNS | 无效 | 查询照样在光猫侧被截住并伪造应答 |
| 关闭光猫 `DnsCMAPIEnabled` / `DnsTunnelMode` | 无效 | 真正开关是 ITMS 注册状态 |
| 给光猫指定上游 DNS | 无效 | 桥接模式没有默认路由，光猫自身上不了网 |
| 杀掉 `ipv4protocol` / `ctsgw_proxyd` | 无效 | 守护进程会重新拉起；钩子在内核层 |
| 拆掉 `ebtables` 的 `DNSREDIR` 链 | 无效 | 那条链只匹配特定域名，不是本次故障源；开机还会重建 |
| 光猫重启 | 无效 | 注册表里状态仍是未注册 |

**教训**：先在配置库里找到「状态机」字段，再动手改；不要从表象（DNS 返回假地址）直接推断是哪一层做的劫持。

---

## 5. 证据链（怎么确认是光猫而不是别处）

按强度从弱到强：

1. **向不存在的 IP 发查询也有应答**：`203.0.113.99` / `198.51.100.7` 这类公网不可达地址，4ms 返回假答案，且应答源 IP 被改写成被查询地址 —— 通配劫持特征。
2. **双口同时抓包**：在主路由所接的物理口能看到 IPv4 DNS 查询帧（几十到几百条），在外线 PON 口为 0 条 —— 查询进了光猫但没出网。
3. **微秒级应答**：查询与应答相差约 90 微秒，不可能完成公网往返；且查询 AAAA 却回 A 记录，类型不匹配。
4. **对照实验**：TCP/53 正常、IPv6 DNS 正常、DoH 正常、直连真实 IP 网页 200 —— 排除运营商认证门、排除线路故障。
5. **注册表实锤**：`PDTCTUSERINFO.Status = 99`；改成 `0` 并重启后，全部测试立刻转正常。
